## 1. A1：级联删除（P2-0a）

`91fff99` 的提交说明把四处缺陷并列写成 `unlink` / `rename` R3 / `rename` R7 / `rmdir`。
实际上来源不同：

| # | 位置 | 缺陷 | 来源 |
| --- | --- | --- | --- |
| 1 | `unlink` | 删 `file` 行，不删 `file_extent` 行 | **architect 报告** |
| 2 | `rename` R3（文件覆盖文件） | 完全不动被覆盖的 inode 与其 extents | **architect 报告** |
| 3 | `rename` R7（空目录覆盖） | 删 `file` 行，但不删它的 extent 行 | **本卡独立发现** |
| 4 | `rmdir` | 与 `unlink` 同形：删 inode 不删 extents | **本卡独立发现** |

**第 3、4 项是怎么发现的**：写 A1 复现测试时，我按"每一种删除/替换路径"逐条枚举，而不是只写
architect 给的两个场景。枚举清单来自 `Namespace` 的公开操作面：`unlink`、`rmdir`、`rename` 的
R3 与 R7 两个覆盖分支。R7 与 `rmdir` 属于同一类（删除 inode 而不动 extents），但 architect 的
报告只覆盖了 `unlink` 与 R3。

这正是收尾清单第 1 条（**枚举所有违反形式**）起作用的又一次实例：给定"删除 inode 时必须级联"
这条规则，违反它的形式有四种，照着操作面列全就能都抓到，靠 review 抽查则依赖报告者的完备性。

**处理**：四处统一改走 `Namespace::delete_inode`，让删除路径无法只删一半。这样即使将来新增
第五种删除路径，只要走这个函数就不会漏。

## 4. B1：并发缺陷（P2-0b）

architect **推理**出四类场景，卡面要求"先证实或证伪"。实测结果：

| # | 预测 | 结果 | 说明 |
| --- | --- | --- | --- |
| 1 | 同文件不同块并发写，size 回退 | **证实** | 40 轮约 25 轮触发；不只是丢长度，是**丢块** |
| 2 | `write_at` × `truncate` 后文件长回去 | 未复现 | — |
| 3 | `write_at` × `unlink` 留孤儿 extent | 未复现 | A1 级联修复后该机制已不存在 |
| 4 | 交叉 `rename` 都过 R9 形成环 | 未复现 | R9 的子树的检查与提交在同一事务内 |

**"未复现"弱于"不可能"。** 测试以 40 轮驱动、断言不变量，但无法证明不存在时序窗口。第 2、3 项
的窗口在理论上仍可能存在，只是本卡未触发。

B1-1 的根因与暴露面评估见 ADR-004 §3.1 第 3 点与 §11 第 2 条；manager 裁决**不在 P2a 前修**
（P1 使用方是顺序 CLI 与单线程基准，无真实并发写同文件的场景；overlay 到来后窗口结构性消失）。

## 5. architect 已确认：k3 断言不过强（可线性化）

原疑问：`k3_concurrent_writes_to_different_blocks_keep_both` 是否过强。

**architect 答复（经 manager 转达，ADR-006 §7.4 @ `7a6cf49`）**：不过强。overlay 无内存层
（§2.5 修订后），每个操作是一个完整事务、句柄互斥锁持有到提交，因此**可线性化**。

于是：不同区间的两个并发写只有两种串行顺序，而**两种顺序的最终字节相同**（区间不重叠），
所以"两者都存活"不是选择一个顺序，而是陈述所有顺序都同意的那一个结果。断言正确。

据此新增四个契约用例，断言形式统一为"结果 ∈ 所有串行顺序结果的集合"：

| 用例 | 场景 |
| --- | --- |
| K3a | 重叠区间并发写——结果等于某一种顺序，重叠区不出现字节交错 |
| K3b | write 与 truncate 并发——两种顺序之一 |
| K3c | write 与 unlink 并发——顺序之一；unlink 在先时 write 失败且不留孤儿（K1） |
| K3d | 交叉目录 rename 并发——至多一个提交（K4） |

全部 `#[ignore]`，作为 overlay 后端的准入门槛。

## 6. 原疑问的留档

提问时的原话：overlay 的语义若为"以最后一次完整操作为准"（并发写不保证叠加），则该断言过强。

**该假设被 architect 否定**（见 §5）：overlay 是可线性化的，不存在"丢弃一方"的语义。

留档原因：这个问题问对了方向——如果 overlay 真采用"最后一次完整操作"的语义，那么准入门槛
就必须改写，否则会误伤正确的实现。契约测试的价值取决于它断言的是真实的契约，不确定时先问
比先写死更省事。

**当前状态**：`k3` 与 `k3a`–`k3d` 全部 `#[ignore]`，在表后端上按设计失败，是 overlay 后端的
准入门槛。
