# 提交与验收流程（负责人定义，2026-10-22）

角色：**user**（负责人，最终决策）· **manager**（任务分配与验收）· **worker**（开发）· **qa**（测试）

## 流程

```
manager 派卡（mailbox，含任务说明+验收标准）
   ▼
worker 开发（特性分支 t<N>/<slug>，不断 main）
   ▼
worker 提交申请（mailbox_reply 原任务邮件：分支、提交哈希、测试输出、ADR/文档路径）
   ▼
manager review（代码 + 架构准则 docs/architecture.md + 规格 §8 提交说明 + 约束红线；不符合架构的修改退回）
   ├─ 不通过 → 退回 worker 修改（同一邮件线程）
   ▼
manager 转交 qa 测试（附：任务说明原文、验收标准、review 关注点、分支/提交）
   ├─ qa 不通过 → 退回 worker（附失败复现）
   ▼
qa 通过 → manager 批准合入
   ▼
worker 合入 main，回信报告合并提交哈希
```

## 规则

1. **任何任务卡未经 QA 通过不得合入 main**（负责人指示，2026-10-22）。
2. 转交 QA 时必须**附带任务说明**（原任务卡内容）与验收标准，QA 据此设计测试，不只测"能编译"。
3. 通信一律走 mailbox：新话题 `mailbox_send`，跟进用 `mailbox_reply`（保持线程）。
4. QA 测试范围至少包含：验收标准逐项、spec §6 对应测试矩阵、崩溃/边界/无效输入用例；性能类验收按 spec §8-6 给原始数据。
5. 争议或规格歧义：worker/qa → manager；影响规格的决策 → 负责人（user），必要时立 ADR。
6. 分支命名 `t<N>/<slug>`；main 只经本流程推进，不直接 push。

## 角色分工（owner 指示，2026-10-23）

- **architect**：架构设计与分析归口——阶段设计、架构问题咨询、ADR 设计输入。不写产品代码、不合入、不 push；验证用 Git Bash + arch-* 前缀隔离 worktree（**一律基于特性分支，不占 `main` 检出**，否则 manager 的文档直提 worktree 无法建立）。分析产物以 `docs/reports/` 文档形式提交到 arch-* 分支，由 manager cherry-pick 进 main；scratch 测试不提交。

### 会话失活后的接手流程（manager 经验，2026-10-24）

会话崩溃（DSH 崩、卡死、上下文耗尽）后，**接力断点几乎总在 manager**：worker 的新会话在等卡、QA 的发现已发出但没人转发，全队静默。观察到的一次实例：worker 与 manager 会话同时卡死，QA 的 FAIL 级分诊请求悬空 4.5 小时。

接手的 manager 按以下顺序恢复（不必等任何人通知）：

1. **git**：`git log --oneline -15`、`git status`、`git branch -vv`、`git worktree list`（worktree 列表是发现别人在做什么的最快线索）。
2. **文档**：`docs/process/`（任务卡、本文件）、`docs/reports/known-issues.md`、相关 ADR。
3. **邮箱**：`mailbox_list` 通读最近线程，先找**未闭环的请求**（别人的提问、失败报告、待派卡）。
4. **先补接力，再做别的**：把悬空任务重派给当前在线的角色会话（卡必须自包含——新会话没有历史）。
5. **核对在途工作**：`git status` / worktree 里别人的未提交改动，避免重复实现（同一缺陷两条线同时动手很常见）。
6. 对外部（qclaw）状态汇报要在发出前核对 worktree 与 git，别把"空闲"写成结论。

规则：不因这次断链而加"FAIL 双发 + 超时升级"（owner 2026-10-24 决定），保持 manager 单点转达；可靠性靠上面这套恢复流程，而不是增加分发面。

### Worker 上下文管理（owner 指示，2026-10-23）

Worker 每完成一张卡的提交申请后、接下一张卡前，compact 一次上下文。任务卡本身是完整自包含的，compact 不会丢失必要信息。目的是防止连续多卡后上下文预算耗尽导致交付质量下降。

## 撤销实验（A/B）的纪律（QA 经验，2026-10-24）

"撤掉修复 → 测试必须变红"是唯一能证明回归测试有效的办法，但它自己也会骗人。两条硬要求：

1. **两个臂必须各自独立的 `CARGO_TARGET_DIR`**。共享目标目录等于把两个臂混进同一指纹空间：实测中出现过
   "本该失败的用例意外通过"，因为 pre 臂跑的是 post 臂的二进制；发现方式是 `--list` 的用例数不同（18 vs 17）。
2. **先分类用例，再做撤销实验**。有的用例在缺陷树上本来就是绿的（被别的机制掩蔽），拿它做撤销实验会得出
   "修复没生效"的错结论。做法：在干净树上跑一遍，红的一类才是 A/B 判据，绿的只能算覆盖用例。
   实例（KI-9）：`缩容 → snapshot/commit → 再扩` 绿（物化把内容搬进 base、`base_limit` 掩蔽旧页，是**掩蔽**），
   而 `缩容 → flush + close + reopen（不 commit）→ 再扩` 红——后者才是持久化路径的 A/B 判据。
3. **两个臂都必须跑在"已提交、工作树干净"的 SHA 上**（`git status --short` 为空再测）。共享工作树的中间态
   （代码已改 + 测试已加 + 文档被手改）一旦被当成"已提交的实现"去跑，会得到"修复有效"的假结论：这时跑的是
   未提交的代码，而另一臂可能来自不同 target，两个臂根本不在同一个作者状态上。

同样地，**测试辅助代码不得有全局状态**：参考模型的 soak 曾用全局 `std::panic::set_hook` 静默 + `catch_unwind`
做失败汇总，结果 `--include-ignored` 时并行跑的其它测试变红**丢失诊断信息**，且汇总过程本身 panic 会永久
留下 no-op hook。结论：不用 `set_hook`，让 libtest 打印（重复一次可接受）。

### QA/验证会话的隔离约定（2026-10-24）

- **临时用例与 worktree 一律放 Windows 路径**（`F:/work/qa-scratch`、`F:/work/qa-<卡>`），**不要用 `/tmp`**：
  write 工具（容器侧）与 Git Bash 的 `/tmp` 在这台机器上不是同一处，会出现"文件写了但 `cp` 找不到"的假故障。
  同一条也适用于 `CARGO_TARGET_DIR`（`F:/work/qa-t-<臂>`）。
- **两臂绝不使用共享工作树**（`F:\work\layer-fs`）的当前树：它随时承载别人的在途改动。R3-1 复验期间
  P2b-2 正在同一棵树上改 `cas-store`，QA 的两个臂各自独立 worktree + 独立 target，因此互不污染——这是
  正面实例，按此执行。
- 验证会话**每 15 分钟至少回一行状态**。失活的代价是协调方只能按超时猜（本团队一天内发生 4 次会话失活）。

### 测试设计的一条教训：首次失败即停会低估缺陷面（2026-10-24）

参考模型 soak 原先 panic 即停，报出 `seed=1000 step=357` 一个形状，"缺陷只影响一个种子"因此成了错误共识。
改成"跑完全部种子再汇总"后，干净树上 **10/10 个种子全部失败**。同一类问题也适用于任何"发现第一个错误就
断言"的统计型测试：**要么汇总全部失败，要么在测试名/报告里写明"首次命中"**，不要让第一个失败充当缺陷面。

### 失败率必须带分母（QA 经验，2026-10-24）

"12 次里红 4 次"与"200 轮里红 2 轮"未必矛盾。P2b-2 的 KI-11 上就出现过这种争执：一方按**测试二进制运行次数**
报（每次运行内部循环 5+10 次发布），另一方按**单次发布**报。换算后两边同量级（p ≈ 1–3%），根本不需要"谁的机器
更怪"来解释。

规则：任何偶发失败的统计必须写清 **分子（失败次数）/ 分母（什么算一次）**，以及分母与"被测动作"的换算关系
（例：一次 `cargo test --test x` = 15 次发布）。否则两个数字会被当成矛盾，浪费一轮排查。

### 探针没生效，等于阴性结论无效（2026-10-24）

P2b-2c 的第一次取证发现：用 dev-dependency 打开诊断 feature **不会**让被测 crate 的依赖图带上该 feature，于是
"提交前 `exists` 断言从未触发"被误读成"文件在提交前一直在"。真实原因是**探针根本没接线**。

规则：任何"断言从未触发/为零"的阴性证据，都必须先证明**探针是活的**（阳性对照：故意注入一次违反，断言必须红）。
这条与"阳性对照先于阴性结论"是同一条纪律的两个应用面：一处针对判据，一处针对观测器。

### 合入前的两条机械检查（QA 经验，2026-10-24）

`--ff-only` 合入**不是**没有风险：若特性分支的基座落后于 main，ff 会把 main 上后来加入的文档**静默回退**
（不产生冲突，因此不会有人察觉）。P2b-2d/2e 上就差点把 KI-11 条目、三张任务卡、QA 判定报告与流程纪律一起
删掉。合入前必须跑：

```bash
git fetch origin                                # 先更新本地 ref，否则下面两条查的是旧快照
git merge-base --is-ancestor origin/main HEAD   # 必须成功，否则先 rebase
git diff origin/main..HEAD -- docs/             # 不得出现 D（删除）
```

**`fetch` 不是可选项**：`--is-ancestor` 只回答"在你本地看到的 `origin/main` 上是不是祖先"，本地 ref 陈旧时它会
给出"通过"而实际已落后。同一轮里出现过三次（删 4 份文档、删判据、删编号列），全部是"检查正确、ref 陈旧"。
另：**manager 也不要在转交 QA 期间往 main 提文档**——那会让分支基座在 review 中途失效；要么等合入，要么在转交
前先告知 worker 需要 rebase。

第二条能抓到"分支里根本没有这些文档"的另一种形态（分支从旧基座切出）。**这两条与"两臂跑在已提交干净 SHA"
同属机械检查，不依赖判断力，因此必须每次执行。**

### 改语义字段前先 grep 断言点（2026-10-24）

`waited_ms` 从"策略常量"改为"实测等待"时，两处既有测试仍 `assert_eq!(waited_ms, MAIN_BUSY_TIMEOUT_MS)`，
于是全量在语义修好之后反而变红。改字段**语义**（不是改名）前，先 `grep -rn "<field>" crates/`，把所有断言点
列出来，改完一并改成"钉事实"。

### 证据的独立性本身也要被验证（2026-10-24）

QA 曾在三个 crate 里各写一个临时探针跑 `Display` 真值，三个 bin **同名**（`qa_display_probe`）又共用 target dir →
cargo 三次跑的是**同一个二进制**，"三份互相印证的独立证据"其实是同一份；她是靠"三份输出 md5 完全相同"才发现。

规则：

1. 临时探针/诊断二进制的**名字必须跨 crate 唯一**（`qa_ov` / `qa_sn` / `qa_ws`），或各用独立
   `CARGO_TARGET_DIR`；
2. 多份"独立证据"要先证明**它们确实来自不同来源**（不同二进制/不同命令/不同实现），否则只是同一次观测的
   三份拷贝；
3. 与"观测器先自证"合并成同一条纪律：**先证明工具能看见已知事实，再证明工具看到的是被测物**。

### 本机测试的不确定性来自环境（KI-11，2026-10-24）

本机有外部进程会删除新建的 `.pack` 文件（约 100 µs 内，见 `docs/reports/known-issues.md` KI-11），因此**全量测试在
本机偶发红**是环境事实：同一 SHA 连跑 13 次里 4 次红，每次失败的测试不同；单跑各 20 次 0 失败。

判定口径：**不接受"重试/吞 `MissingPack`"来换取绿色**（那会掩盖真实删除）；改用"逐项验证 + 多次连续绿 +
把环境不确定性写进报告"。任何以"全量无条件绿"为前提的门禁，在本机都是"等运气"。

### 角色 handoff 文件（QA 经验，2026-10-24）

同一天里全队会话失活四次（DSH 时期 manager/worker，各一次；今天 worker、QA 各一次）。每次重新接手都要重读文档与邮箱，
成本约两小时。对策：**每个角色在卡与卡之间维持一份 handoff 文件**（放在自己的 scratch 目录或 `docs/process/`），至少五段：

1. **当前状态**（哪些卡已合入、哪张卡进行到哪一步）；
2. **我的产物路径**（清单、探针、隔离 worktree、报告草稿）；
3. **工作纪律**（该角色反复踩过的坑与固定动作）；
4. **下一步**（接手者第一件事做什么）；
5. **角色边界**（谁写产品代码、谁只做验证、谁能动 main）。

失活后接手者第一件事读它，而不是从 git log 重推。QA 的 `qa-handoff.md` 是第一个样例。

### fixture 里的"共享/不同"必须由测试自己证明（2026-10-24）

P2b-6 的 C11'（共享页对两个父亲都可见）第一版是**空的**：两个 extent 叶写的是**同一份字节**，而内容寻址下
"同一份字节"就是**同一个 oid**——于是"共享 chunk 的两个父亲"退化成"自己共享自己"，测试看起来在测共享，
其实什么都没测。修法：让两个叶**对象不同**、但都指向**同一个 chunk**，并同时断言"页内 2 条 extent 项被折叠
成 1 个不同子对象"。

规则：凡测试依赖"两个东西共享同一对象"或"两个东西不同"，**都必须由测试自己证明 oid 相等/不等**，不能假定；
内容寻址（CAS）下尤其容易把"值相同"误当"对象不同"。

这是本轮第二次出现"测试看起来在测 X，其实测了 Y"（第一次是 T2 里 `let n = 3; assert_eq!(n, 3)` 的恒真断言）。
两者的共同点是：**断言的两端都没有接到被测物**。

### 替换式注入必须先断言"确实改到了"（2026-10-24）

P2b-6 验证 T3 时，worker 把 `commit.commit_id` 误标成 `RootSource` 想做一次"注入必红"的对照——**测试没红**。原因不是判据太弱，
而是他的替换文本没匹配上（原文有排版差异），**实际什么都没改**。差一点就把"没改"当成"判据不够强"的证据，转头去加强一个
本来已经有效的判据。

规则：凡"改一处代码/配置看测试是否变红"的注入，**必须先断言这次改动真的发生了**：

- 文本替换：`assert text.count(old) == 1`（并要求 `old` 与 `new` 不同）；
- 文件替换：比对替换前后的哈希；
- 开关注入：读回开关状态。

这与"探针必须先证明自己是活的""观测器先自证""证据独立性也要自证"是同一条纪律的第四个应用面：**先证明"我确实改变了它"，
再证明"它确实变红了"**。

### "重跑就绿"不是解释（2026-10-24）

P2b-6 里一次全量跑到 `321 passed / 1 failed`，worker 没抓到失败测试名就重跑，第二次绿了，于是按绿的那次写进提交说明。
后续定位到机制：`plan` 的纯读断言在两次 `index()` 之间比 `(路径, 长度)`，而**开关第二条连接会 checkpoint WAL**，`-wal`
长度随之变化——断言没错，**测量方式错**（与 §6.1 排除 `-shm` 同一类）。

规则：**偶发红必须抓到失败测试名并说出机制，才能写进提交说明**；说不出来就写"未解释的偶发红"并留原始输出。用"重跑就绿"
覆盖一次真实的红，等于把 flake 留在库里，而且下一次它会以更难查的形态出现。

### 拒绝必须配一条出路（2026-10-24）

`branch delete` 的第一版拒绝"分支上还有 workspace"——拒绝本身正确，但**当时没有任何 CLI 手段把 workspace 移开**，于是用户
被永久锁在门外（测试就是死在这里）。补了 `workspace discard` 之后，"拒绝 → 有路可走"才成立。

规则：任何"因为前置条件不满足而拒绝"的入口，必须在同一张卡里给出**解除该条件的可操作路径**（另一个命令、一个参数、或一段
明确的指引）。只拒绝不解锁，等于把正确的防御变成不可用的产品。测试要覆盖"拒绝 → 走完出路 → 成功"这条完整链路，而不只是
断言拒绝发生。

### 丢掉一个根之前，先数清还有几个根（2026-10-24）

P2b-6 的 K5c（"两个根都丢掉后共享页被回收"）第一版**永远不可能通过**：`Repo::snapshot()` 会把 workspace 的 `base_root` 移到
它刚发布的树上，于是 workspace 行成了**第三个根**；共享页始终可达，`freed` 永远为空。测试本身没报错——它只是静默变成了
"测 workspace 而没在测快照"。

规则：**任何"丢掉一个根 / 让某对象变不可达"的测试，必须在注释里点清当前还存在哪些根**（branch head、`branch_log`、
`snapshot` 行、workspace `base_root`、overlay `pending_root`/`sealed_content`），并显式处理"顺手造出来的根"（例如
`restore(head, discard)` 把 workspace 拉回分支）。否则测的往往是"最后一个没被注意到的根"。

同一条纪律的另一面：**同一进程里持有 `Repo` 时不要调用需要独占的收集器**——它会拒绝自己的调用者（`StoreInUse`），
这一点在 P2b-6 的 CLI 上也现过一次（`repo.gc()` 必须改成自由函数）。
