## 1. 为什么"生产路径探针 + 阳性对照"而不是看代码或看注释

"fsync 都在事务外"是**顺序断言**，不是可读出来的性质：事务边界由 SQLite 决定，fsync 由本仓库的
`durability` 层发出，两者分散在不同 crate。三种常见"证明"都不成立：

| 做法 | 为什么不成立 |
| --- | --- |
| 代码注释/提交说明声明 | 声明不是证据；后续重构静默改变顺序时无人发现 |
| 只看事件日志里"没有 sync 落在 txn 内" | 探针没接线时日志为空，断言恒真（假绿） |
| 用测试专属的旁路实现来记录 | 测的是旁路，不是生产路径 |

所以判据由三件事组成（细节见卡片 A–C）：

1. **钩子埋在生产函数里**（`durability::{sync_file, sync_directory}`、`rename_replace`、pack 写完点），
   feature 门控，默认不编译进消费者；
2. **事务边界由 SQLite 的 `trace` 独立给出**，不依赖探针自报；
3. **非真空性 + 阳性对照**：既断言"观测到了预期数量的事件"，又提供一个"在事务内注入一次 sync"
   的注入点，要求同一检查器**失败**。后者是防止"探针坏了所以永远绿"的唯一手段。

期望序列按 ADR-008 §5 第 4 条是**每 pack 一块**：
`PackWrite → SyncFile → Rename → SyncDir → TxnBegin → 只 INSERT → TxnCommit`。

### 1.1 重试让"每 pack 恰好一次"失效，必须按 attempt 分组

`tmp/` 被并发 opener 清扫时，staging 会**从零重写**（新临时名）。若探针不区分尝试，同一个 pack 会
出现多组 `PackWrite/SyncFile`，把"每 pack 一次"的计数判据变成假失败。判据因此写成：

- 失败/中止的尝试：**零** `TxnBegin`（证明从未进入发布阶段）；
- 只有最后一次成功尝试参与 V1–V7 与 `2k` 计数；
- 并发 open + publish 的用例只断言"事务内零 sync、事务数 == 成功 pack 数、索引唯一、`verify` 干净"，
  并记录重试次数——失败尝试的 sync 也在事务外，属可接受形态。

## 2. 锁持有判据：为什么是自校准边际成本，而不是比值或绝对毫秒

目标不是"快"，而是"**持锁时间不随对象数增长**"。三种写法的问题：

- `H(1000) ≤ k·H(10)`：`H(10)` 由**一次** WAL 提交的 fsync 主导，噪声与机器状态同量级，k 取小会 flaky、
  取大则失去判别力；
- 绝对毫秒上限：磁盘差异（NVMe vs 网络盘）能差两个数量级，阈值只能越调越松；
- 只看 `H(1000)` 单点：无法区分"常数项大"与"线性增长"。

采用的判定式（卡片 D）：

```text
S = 同进程对 scratch 文件 20 次 sync_file 的中位耗时（同一磁盘）
m = (H(1000) − H(10)) / 990
PASS ⇔ m ≤ S/10 且 H(1000) ≤ 100·S
```

`H(n)` 是 `BEGIN IMMEDIATE` 前到 `COMMIT` 后的墙钟，单事务 n 个唯一对象，6 轮丢首轮、每轮取 max
再取中位。诚实实现的 `m` 是每行 INSERT 的量级（1–5 µs）；若每对象一次 fsync，`m ≈ S`，被 10× 判红。
`S` 自校准把"磁盘"这个变量从阈值里消掉。阳性对照（事务内每对象注入一次 sync）必须让该判定式失败，
否则"没测到"与"没发生"无法区分。

## 3. `tmp/` 回收：双向竞争、方案评估与被否理由

### 3.1 事实与缺口

ADR-002 §7 第 5 步"打开时清 `tmp/`"的安全性论证是：tmp 中内容从未发布，删掉不会丢已发布数据。
这在**安全性**上正确；§7.0 也处理了清理方遇到 `NotFound`/`PermissionDenied` 的情况。缺的是**另一个
方向**：清理方会删掉**存活进程正在 staging** 的文件，发布方拿到 `Io(NotFound)`（实测约 1/6）。
这是**活性/可用性**缺口，不是数据正确性缺口，因此不能用"删了也不丢数据"来回应。

### 3.2 方案评估

| 方案 | 评估 | 结论 |
| --- | --- | --- |
| (a) `open` 在独占锁内清理 | staging 期间发布方**不持任何锁**（只有最后那个短事务），清理窗口与写窗口仍然重叠；要真解决得引入跨进程读写锁，或让 stager 在长读事务里写文件 | 不够，否决 |
| (b) 只清"比自己更老"的条目（pid/时间戳） | 可行，但引入"时间策略"这第二套回收规则，要与 staging 最长时长对齐、要测，且与 P2b-6 的 GC 回收职责重复 | 否决（不是错，是多余） |
| (c) 每进程独立 `tmp/` 子目录 | 清理方仍不知道哪个子目录属于活进程；`clear_temporaries` 对目录是递归删除，误删会**一次抹掉整批** staging，比单文件更糟 | 单独做更糟，否决 |
| (d) 有界重试 + 写明"tmp 是可丢弃区" | 承认 tmp 的语义，成本是一次尚未发布的重写；需要"新临时名从零重写、只包 staging、耗尽报原始错误"三条约束 | **P2b 内采用** |

### 3.3 长期：回收权收归离线 GC（P2b-6）

ADR-008 §6.1 已论证 GC 必须离线独占（有使用者即拒绝），§6.3(c) 已把"删除 `tmp/` 全部"交给 GC。
因此 P2b-6 起**常规 `open` 不再清扫 `tmp/`**，GC 在独占期间回收：

- 构造性消除竞争：GC 运行时不存在活 stager，不需要锁、时间阈值或子目录约定；
- 代价是崩溃残留会留到下一次 GC（与 ADR-002 §7.1"孤儿只读不删"的取舍同向）；
- `Store::create` 保留清扫（新库没有并发写者）；`Opened.temporaries_removed` 的语义随之收窄为
  "仅 create 模式可能非零"。

**一条硬约束**：GC 的临时标记库（ADR-008 §6.3 的 `gc-<id>.sqlite`）**不得放在 `tmp/`**——常规
`open` 的清扫能删掉它（opener 在 `validate` 之后即可清扫，不需要 GC 的排他锁）。放 store 根下独立
名字，GC 结束自删。

### 3.4 必须钉住的测试（P2b-2 与 P2b-6）

1. N 线程发布同一对象：索引唯一、pack 存在、`verify` 干净，报告偶发率与重试次数；
2. 手动清 `tmp/` 模拟并发 opener：staging 从零重写后发布成功，**不发布任何部分内容**；
3. P2b-6：崩溃残留的 `tmp` 文件在常规 `open` 后**仍在**，GC 后被删；
4. P2b-6：GC 运行中 `Repo::open` 被拒（StoreInUse），不出现"清理方与 GC 互删"。

## 4. 两个格式边界（结论在卡片，理由在此）

- **尾部 48 B**：`magic "WPK1"(4) + u32 count(4) + u64 frames_len(8) + BLAKE3(32)`。`count` 是
  **物理帧数**，不是索引行数：并发 `INSERT OR IGNORE` 跳过时帧仍在、行缺失（死字节，GC 重打包回收），
  此时只能断言 `count ≥ 行数`。空 pack 不产生（无新对象 → 0 pack、0 sync）。
- **单对象读不读尾部**：判据是"总读字节 == 该对象帧长"且"读取区间并集 ⊆ `[offset, offset+length)`、
  不含 `[file_size-48, file_size)`"。观测点必须在 pack 读取器的 `read_exact_at`，不能在 `Store::get`
  返回处——后者只能证明返回值正确，证明不了读了多少。
