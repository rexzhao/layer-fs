## 0. 测量规则（本报告的全部数字都受这几条约束）

这几条不是形式要求——本报告在成形过程中**两次因为违反它们而得出了错误结论**（见 §8）。

| # | 规则 | 为什么 |
| --- | --- | --- |
| R1 | **每场景 ≥3 次重复，报告全部原始 run**（min/median/max），不只给汇总 | 参考盘的提交延迟方差达 5 倍；单点数字在这台机器上没有意义 |
| R2 | **探测必须持续足够长以穿透写缓存** | 200 次操作的探测报告 0.9 ms/对，20,000 次持续写入是 3.9 ms/对——差 4.3 倍，全部是缓存吸收 |
| R3 | **每个数字旁注明载荷特征**（同内容块 vs 互异块、对齐 vs 非对齐、冷盘 vs 热盘） | 同内容的块会被去重成 1 个对象，此时"写吞吐"测的是去重 |
| R4 | **报告测的是哪块盘、哪个目录** | 基线与环境绑定；换机器需重跑 |
| R5 | **不取最佳单次值，不宣称盘间优劣**（本卡裁决） | 本卡目的是建基线，不是选盘 |

## 2. 提交延迟（一切小文件数字的根源）

每次变更型 API 调用是一个独立事务，`synchronous=FULL` 强制每次落盘（ADR-002 §9、ADR-003 §7 的刻意选择）。因此小文件吞吐由 **提交次数 × fsync 延迟** 决定。

### 2.1 短时探测 vs 持续写入（R2 的实证）

同一台机器、同一份代码、同样的一对操作（`create` + `write_at`）：

| 测量方式 | F: | C: |
| --- | --- | --- |
| 200 次操作的探测（10 次重复，P50） | 0.93 ms/对 | 2.76 ms/对 |
| **20,000 个文件持续写入** | **78.7 s ≈ 3.9 ms/对** | **76.5 s ≈ 3.8 ms/对** |

**两个结论，都需要记住：**

1. 短时探测比持续写入**快 4.3 倍**（0.93 vs 3.9），因为小块写入被磁盘写缓存吸收。任何用探测得出的吞吐预测都会严重偏乐观。
2. **在两块盘上，持续写入的速度基本相同**（78.7 s vs 76.5 s）。短时探测显示出的 3 倍盘间差异是缓存伪影。

### 2.2 延迟方差

20,000 文件的写入按每 2,000 个一段切开，段间耗时（秒）：

```
segment=0 files=0..2000      seconds=8.6   us_per_pair=4304
segment=1 files=2000..4000   seconds=8.1   us_per_pair=4071
segment=2 files=4000..6000   seconds=7.8   us_per_pair=3901
segment=3 files=6000..8000   seconds=4.1   us_per_pair=2044
segment=4 files=8000..10000  seconds=1.9   us_per_pair=958
segment=5 files=10000..12000 seconds=1.9   us_per_pair=934
segment=6 files=12000..14000 seconds=6.2   us_per_pair=3092
segment=7 files=14000..16000 seconds=8.6   us_per_pair=4281
segment=8 files=16000..18000 seconds=9.3   us_per_pair=4665
segment=9 files=18000..20000 seconds=8.1   us_per_pair=4041
total: 64.6s for 20000 files（该次运行的独立复核）
```

**关键观察：耗时在 1.9–9.3 s 之间随机波动，不随文件数单调增长。** 因此：
- 不是索引膨胀（否则后段持续变慢）；
- 不是算法退化；
- 是这块盘的写入延迟方差约 **5 倍**，与存储位置无关。

这就是 R1 存在的原因：在这种方差下，任何单次数字都可能是 2 ms 也可能是 9 ms。

## 4. 大文件（1 GiB）

### 4.1 顺序写：**两个数字，标签必须一起读**

| 场景 | 每块内容 | 对象数 | 1 GiB 耗时 | 吞吐 | 测的是什么 |
| --- | --- | --- | --- | --- | --- |
| `gb.rs` | **16,384 块全相同** | **1** | 约 31 s | ~33 MiB/s | **去重上界**，几乎无对象写入 |
| `acceptance_scale.rs` S3 | **16,384 块互不相同** | 16,384 | **146.7 s（P50）** | **~7 MiB/s** | **真实写路径** |

**3 次重复，全部原始 run**（`baseline -- large --repeat 3`）：

| run | 顺序写 1 GiB | 吞吐 |
| --- | --- | --- |
| 0 | 105.3 s | 9.7 MiB/s |
| 1 | 170.6 s | 6.0 MiB/s |
| 2 | 146.7 s | 7.0 MiB/s |

| 汇总 | 值 |
| --- | --- |
| n=3 | mean 140.9 s，**P50 146.7 s** |
| 范围 | 105.3–170.6 s（**1.6 倍方差**） |

**注意方差**：这组数字的离散度达 1.6 倍，正是 §2.2 所描述的该盘特性。**P1 写入基线取 P50 = 146.7 s（约 7 MiB/s）**，单次 192 s 与单次 105 s 都不应被引用。

31 s 作为"全去重上界"保留并标注（载荷特征：16,384 块全相同 → 1 个对象）。

**随机写**（64 次 64 KiB 改写）：1.107 / 1.187 / 1.408 s，P50 1.19 s，约 54 次/秒。

写放大：每块 64 KiB 都经历 `put`（tmp → fsync → rename → 同步目录 → 索引提交）+ 一次命名空间事务，因此写放大约 **2×**。

### 4.2 随机读（4 KiB，跨 1 GiB）

3 次运行 × 500 次读 = 1,500 个样本：

| 指标 | 单次验收运行（200 次） | **重复组（1,500 次）** |
| --- | --- | --- |
| P50 | 754 µs | **867 µs** |
| P95 | 1,227 µs | **1,661 µs** |
| P99 | 1,456 µs | **2,040 µs** |
| min / max | — | 262 µs / 2,965 µs |
| 读放大 | 200/200 次断言通过 | 每次读 1–2 个对象 |

重复组的数字更高，因为样本量大 7.5 倍，尾部长了出来——单次 200 样本低估了 P95/P99。

### 4.3 内存有界的证据

1. **读放大计数**（生产指标，非测试钩子）：200 次随机读每次只 `get` 1–2 个对象。加载整文件的实现会是 16,384。
2. **写路径不持有整文件**：按 64 KiB 块推进，测试本身只持有 64 KiB 缓冲。

## 5. 去重（spec §6 第 1 项）

100 个路径写入同一份 512 KiB 内容，**3 次重复**，三次完全一致：

```
dedup,run=0,paths=100,logical_bytes=52428800,unique_canonical_bytes=524288,objects=1,stored_bytes=65550,dedup_saved_bytes=51904512,dedup_ratio=100.00
dedup,run=1,paths=100,logical_bytes=52428800,unique_canonical_bytes=524288,objects=1,stored_bytes=65550,dedup_saved_bytes=51904512,dedup_ratio=100.00
dedup,run=2,paths=100,logical_bytes=52428800,unique_canonical_bytes=524288,objects=1,stored_bytes=65550,dedup_saved_bytes=51904512,dedup_ratio=100.00
```

| 指标（spec §5.6 命名） | 值 |
| --- | --- |
| `logical_bytes` | 52,428,800（50 MiB） |
| `unique_canonical_bytes` | 524,288（512 KiB） |
| 对象数 | **1** |
| `stored_bytes`（磁盘实际字节） | 65,550 |
| `dedup_saved_bytes` | 51,904,512 |
| 去重比 | **100.00×** |

`stored_bytes` 为 65,550 而非 524,288，因为 512 KiB 全为 `0x5A`，按 64 KiB 分块后 8 块相同 → 去重为 1 个对象（65,536 + 14 字节信封）。**载荷特征：全相同内容**（R3）。

## 7. 复现命令

```sh
# 环境
rustc --version && cargo --version && cargo llvm-cov --version

# 四件套（常规回归，须 ≤2 分钟）
cargo build --workspace
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check

# 性能基线（方案 A：单盘 F:，每场景 3–5 次）
export WCAS_TEST_ROOT=/f/fs-bench
cargo run -p fs-api --release --example baseline -- dedup --repeat 3
cargo run -p fs-api --release --example baseline -- large --repeat 3
cargo run -p fs-api --release --example baseline -- small --repeat 3

# 验收矩阵重场景
export WCAS_ACCEPT_FILES=100000
cargo test -p fs-api --test acceptance_scale --release -- --ignored --nocapture

# 覆盖率
cargo llvm-cov --workspace --summary-only
```

**环境变量语义**：

| 变量 | 作用 | 默认 |
| --- | --- | --- |
| `WCAS_TEST_ROOT` | 重场景与基线的写入根目录 | `%TEMP%` |
| `WCAS_ACCEPT_FILES` | S2 的文件数 | `1000`（完整验收设 `100000`） |

**复跑期望**：同一台机器上应落在本报告的分布范围内。**注意 §2 的方差**——单次复跑可能比中位数慢 2 倍以上，这属正常。若显著超出分布，先查磁盘剩余空间与后台负载。

## 8. 过程记录：本报告两次更正了自己交付的数字

按 manager 要求记录，因为两次都是**违反 §0 规则后被迫更正**，而这正是规则存在的理由。

### 8.1 第一次：31 s 的 1 GiB 数字被当作写吞吐

T4 交付时，我把"1 GiB 写入 31 秒"当作写吞吐报给了 manager 与 QA。该测量写的是 16,384 个**内容完全相同**的块，被去重成 **1 个对象**，所以几乎没做对象写入。用互异块重测是约 192 秒，**差 6 倍**。

**违反的规则**：R3（未注明载荷特征）。
**触发更正的机制**：执行 T5 S3 时改用互异块。

### 8.2 第二次：7 倍的盘间差异是缓存伪影

我在阶段汇报中称 F: 比 C: 快 7 倍（原文 3–7 倍，随测量批次变化），依据是**单次 200 次操作的探测**。按裁决要求做重复测量后：短时 P50 确实差 3 倍（0.93 vs 2.76 ms），但**持续写入 20,000 文件后两者几乎相同**（78.7 s vs 76.5 s）。

**违反的规则**：R1（无重复）+ R2（探测未穿透缓存）。
**触发更正的机制**：manager 要求每项 3–5 次重复。

### 8.3 沉淀

- R1–R5 写入 §0，约束后续所有基准；
- ADR-004 §13 收尾清单第 4 条（性能数字配载荷特征）已加；
- 两次更正均记入 T5 提交说明，不追责，但**报告里每个数字从现在起必须带测量条件与重复次数**。
