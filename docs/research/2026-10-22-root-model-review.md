# Root 数据模型与事务协议审查（owner 插入任务，2026-10-22）

状态：manager 架构审查结论；四个问题的直接回答 + 对开发计划的修正。
背景：T3（D+ 方案，owner 已确认）实现于 5c2789f，QA 验收进行中。本文档固化审查结论，供 ADR-003 补强（T4 卡携带）与 P2 设计约束（现在前置）。

## Q1：目录条目、inode、文件内容引用如何对应一个确定 Root？

**现状（D+）：内容意义上不对应。** Root 记录是发布点标记（root_id/parent/op/时间戳），不含任何内容身份；目录条目与 inode（file 表）是可变共享表，属"当前树"而非任何 root；file.content_root → ObjectId 是不可变的内容身份，但"哪个 root 拥有哪些 content_root"的映射只存在于当前表。root N 与树状态的对应是纯时序性的（op N 之后、op N+1 之前），且被后续操作覆盖。

这是 D+ 的既定语义（owner 2026-10-22 确认），规格 §3 的数据模型（FilesystemRoot{inode_table_root: ObjectId}）描述的是内容根形态——即 P2 Snapshot 的目标形态，不是 P1 的。

**修正**：无（符合已批方案）。但 ADR-003 必须把这四问写成一节直接回答（现为分散的"局限"表述，读者拼不出来）。

## Q2：新版本产生后，旧 Root 如何在不依赖当前表状态的情况下读取？

**现状**：root 记录本身可独立读取（append-only 表行，含 parent 链）；其**树状态不可读**——已被可变表覆盖。P1 既定局限。

**P2 必须满足的约束（本次审查前置确立）**：
1. Snapshot = 把当前树**物化为纯 CAS 对象图**：目录页（role 5/6）、inode 表（role 7）、根对象（role 8，ADR-001 预留），旧快照经对象根读取，**零表依赖**——这是 LayerFS overlay→commit 模式的等价物；
2. 快照编码的页尺寸/条目数等参数冻结进 Store Policy（同 CDC profile 的先例）；
3. **P2 Branch 的 CAS 令牌是快照根（内容身份），不是 D+ 的 op 链 head**——op 链是审计序列，不是版本语义。此点现在写明，防 P2 误用。

**修正**：P2 任务拆分显式包含"快照格式 ADR"；上述三条约束进 ADR-003 演进路径节（T4 卡携带）。

## Q3：对象已写入 CAS，但 Namespace 事务失败时如何处理？

**现状（ADR-003 §6 定序，无需修正）**：对象先 put（发布进 store 索引）→ namespace 事务引用。事务失败 → 对象成为 **store 级孤儿**（有索引行、无命名空间引用）。处理：容忍（只读、不删；内容寻址天然幂等——后续同内容 put 直接复用）；回收归 P2.11 GC（根集合 = 各命名空间当前树 + 快照根）。

**两条方向性不变量（ADR-003 应显式化）**：
- 命名空间**绝不悬空引用**（失败方整体回滚，引用从未提交）——永远成立；
- 对象**可以孤儿**（无害、可复用）——可能成立。
反方向（悬空引用）不存在。

**补充修正**：verify 工具（T4/T5）增加**命名空间→对象闭包校验**（遍历全部 file.content_root，确认存在于 store）——这替代逐操作依赖验证（后者在 D+ 下是 O(树)/op，不可接受；规格 §4"发布 Root 前验证依赖"由 put-先于-引用的定序 + 闭包校验共同满足）。

## Q4：两个进程同时更新 Namespace，如何保证只有符合预期版本的更新成功？

**现状**：P1 语义 = 每操作单事务 + 后写生效（owner 已批）。并发防护分三层：① IMMEDIATE 事务串行化；② 同路径**创建**冲突被检测（第二方见类型化 AlreadyExists——事务隔离 + PK 约束）；③ 同路径**写**为后写生效（文件系统常态语义，如两个进程写同一文件）。**没有**"预期版本"（CAS）检查——规格 §4 明文将 CAS 归 P2 Branch Head（"compare-and-swap / 带预期版本…并发冲突返回明确错误，不静默覆盖"），P2 的令牌是快照根（见 Q2）。

**开放选项（呈 owner）**：若希望 P1 即提供乐观并发（fs-api 写操作带 expect_head 参数，不符报类型化冲突），成本小（namespace 层事务内校验 head_root，约 20 行），但扩 P1 API 面。**manager 建议不加**：P1 消费方（单机 CLI/T5 基准）用不到；P2 Branch 的正确令牌是快照根而非 op-head，现在加会引入错误的版本语义。
